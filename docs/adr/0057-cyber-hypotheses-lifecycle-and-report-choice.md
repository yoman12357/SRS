# ADR-0057: Complete cyber assessments and explicit report formats

The user requests useful threat/risk sections for every supported cybersecurity
project, a defensible SDLC recommendation, and IEEE/Normal choices after analysis.
No new live model generations are authorized for this implementation check.

Extend source-linked hypothesis rules beyond narrow modal phrases. Derive
account/permission/revocation/change/integration/monitoring scenarios only from
the relevant source capabilities. Always retain applicable hypotheses and linked
risks; a model's ordering cannot erase them. Label these as derived planning
hypotheses, never observed vulnerabilities or approved new product controls.
Likelihood/impact remain unassessed unless the source supplies ratings.

Keep versioned deterministic SDLC scoring. Distinguish explicit delivery facts
from derived security, operational, integration and deployment factors, each with
source IDs and a rationale. Derived suitability must not invent budgets, release
cadence, regulations, stakeholder availability or calibrated probabilities.
Expose missing decision factors and provisional recommendations. Local Qwen
explains the recommendation and groups work; the coordinator retains exact
requirements, actual test references and methodology-specific phases.

IEEE and Normal generate the same canonical document. The choice controls the
reader and existing primary/full export query, persisted per project in local
browser preferences. Show analysis before generation. IEEE retains its numbered
core and adds clearly separated threat, risk and SDLC appendices; Normal uses the
existing full section-wise report. Format switching never reruns inference or
changes canonical approval hashes. No new provider, framework or API route.

Check with unit/API mocks, frontend tests, build, and synthetic PDF inspection.
Do not run real Ollama generations in this task. Live semantic acceptance remains
unverified until the user authorizes another run.
